# 2.3.1 Software Design

Project WALRUS is implemented as a three-tier Internet of Things (IoT) system. Each tier is developed in a separate repository and runs on a distinct runtime: the **Embedded Firmware** (C/C++ on an ESP32 microcontroller) gathers physical sensor data and actuates the purification hardware; the **Cloud and Server Infrastructure** (Python on the Vercel serverless platform, backed by Supabase managed PostgreSQL) persists telemetry and brokers commands between the device and the user; and the **External User Interface** (a React Native mobile application built with the Expo framework) presents real-time data to the operator and accepts manual control input. The three layers communicate exclusively through HTTPS request/response cycles and the Supabase Realtime WebSocket protocol, allowing each tier to be independently deployed, versioned, and replaced.

The remainder of this section details the design of each tier, the rationale for the chosen technology stack, and the data-flow contracts that bind the system together.

---

## 1. Embedded Firmware Design (ESP32)

The embedded firmware is written in C++17 using the Arduino framework, built with the PlatformIO toolchain, and deployed to an ESP32-WROOM-32 development board. The firmware is organized as a single non-preemptive cooperative loop (`loop()` in `src/main.cpp`) that runs three concurrent timing schedules: a 500 ms fast loop for sensor sampling, actuator control, and cloud synchronization; a 5 s slow loop for the DS18B20 temperature conversion (which is inherently latency-bound); and a real-time clock check against the network-synchronized local time (Philippines Standard Time, UTC+8) for all schedule-driven decisions.

### 1.1 Architecture: Finite State Machine

WALRUS implements its operational behavior as an implicit finite state machine (FSM) whose current state is computed once per fast-loop iteration from a fixed priority order of conditions, rather than as an explicit `switch`/`enum` graph. The state name is serialized into every telemetry payload so that downstream consumers can interpret the device's mode without inferring it from raw actuator flags.

The six operational states are:

| State | Trigger condition (in priority order) | Actuator implication |
|---|---|---|
| `Sleeping` | Current local time is within the configured sleep window (default 17:00–08:00 PST), **or** the user has set a manual sleep flag via the mobile app. | All relays driven HIGH (off); sensors continue to be read for telemetry. |
| `Heating` | Peltier-window time-of-day check is true, the Peltier ON-phase of the duty cycle is active, and the float switch reports water in the basin. | Peltier relay LOW (on); intake and collect pumps forced off. |
| `Filling` | Peltier is scheduled but the float switch reports no water in the basin. | Intake pump LOW (on) until water is detected; Peltier held off pending fill. |
| `Collecting` | Collect-pump duty cycle is in its ON phase (default 5 s out of every 30 min) and Peltier is not active. | Collect pump LOW (on). |
| `Refilling` | Outside the Peltier window, intake pump is active because float switch reports no water. | Intake pump LOW (on). |
| `Monitoring` | Default state when no other condition is met; the system is online and idle, awaiting either the next scheduled event or sensor change. | All relays off. |

State transitions are evaluated every 500 ms by `updateFastSensors()` in the priority listed above. The `Sleeping` predicate (`isSleeping || isInSleepHours()`) short-circuits all actuator logic, ensuring that the system is electrically inert during the configured sleep window regardless of any pending overrides. The Peltier-window check (`peltierShouldRun()`) computes the duty cycle as `((minute_of_day − peltier_start) mod peltier_cycle_minutes) < peltier_on_minutes`, which produces the documented 12-minute-on / 18-minute-off pattern within a 30-minute repeating cycle.

### 1.2 Sensor and Actuator Interface

**DS18B20 Basin Temperature (OneWire Protocol).** The DS18B20 is wired to GPIO 22 and read via the OneWire one-wire protocol, abstracted through the `OneWire` and `DallasTemperature` Arduino libraries. To avoid blocking the 500 ms fast loop for the ~750 ms required by the sensor's 12-bit conversion, the firmware uses the library's non-blocking mode: `setWaitForConversion(false)` is called at startup, then `requestTemperatures()` is issued every `TEMP_INTERVAL = 5000 ms`, and the result is harvested by `getTempCByIndex(0)` after a `TEMP_WAIT_MS = 800 ms` delay tracked by `tempRequested` and `tempRequestTime`. A range check (`-50 < t < 100`) rejects implausible reads that indicate sensor disconnection or bus error. The latest valid value is held in `currentTempC` and used by every subsequent fast-loop iteration as well as included in each telemetry packet.

**TDS Analog Sensor.** The Total Dissolved Solids sensor is connected to ADC channel GPIO 34 and sampled every fast-loop iteration. The raw 12-bit reading (0–4095) is converted to a voltage assuming a 3.3 V reference, then mapped to PPM through the manufacturer's third-order polynomial calibration curve:

```
TDS_raw = (133.42·V³ − 255.86·V² + 857.39·V) · 0.5
```

The result is then temperature-compensated against `currentTempC` using the standard 2% per °C drift coefficient, yielding `currentTds` as an integer PPM value.

**Float Switch.** A normally-open float switch on GPIO 33 (configured with internal pull-up via `INPUT_PULLUP`) reports water presence. Closed-to-ground (`LOW`) indicates water detected; open (`HIGH`) indicates no water. The boolean `floatWaterDetected` is recomputed every fast-loop iteration and drives both the intake-pump control logic and the conditional Peltier activation. (An ultrasonic distance sensor was used in earlier firmware revisions but was deprecated in v12 in favor of the simpler, more reliable float switch; the `clean_level_cm` field is retained as `NULL`-able in the data schema for backward compatibility and future re-introduction.)

**Relay-Controlled Actuators.** Three actuators are controlled through an active-LOW relay module:

- **Intake micro submersible pump** on GPIO 26 (relay IN1) — fills the basin from the source reservoir when the float switch reports no water.
- **Collection micro submersible pump** on GPIO 27 (relay IN2) — drains the basin's distilled output into the storage container; operated on a configurable duty cycle (default 5 s ON per 30 min, suspended whenever the Peltier is active to ensure exclusive electrical access).
- **12 V Peltier thermoelectric module** on GPIO 32 (relay IN3) — heats the basin to accelerate evaporation; operates only within the configurable time-bound window (default 10:30 AM to 2:30 PM PST) on a 12-minute-ON / 18-minute-OFF duty cycle. When the Peltier is scheduled but the basin is empty, the firmware enters the `Filling` state, runs only the intake pump until the float switch closes, and then transitions to `Heating`.

Each actuator's automatic logic can be overridden from the mobile application through a per-actuator string command (`"auto" | "on" | "off"`) carried in the cloud-sync response. The override is evaluated ahead of the auto logic in `updateFastSensors()`, so an `"on"` override forces the relay LOW unconditionally on the very next fast-loop tick.

### 1.3 IoT Telemetry and Connectivity

**Network Stack.** On boot, `setup()` initializes WiFi in station mode against credentials embedded in firmware. After association, the firmware performs an NTP synchronization via `pool.ntp.org` and `time.nist.gov` with the timezone offset configured for UTC+8 (Philippines Standard Time, no daylight saving), and blocks until `getLocalTime()` succeeds — guaranteeing that all subsequent schedule-based logic operates on accurate wall-clock time. A non-blocking WiFi reconnect attempt is triggered every 10 s while disconnected, allowing the firmware to recover from transient outages without locking up the main loop.

**Cloud Synchronization.** Every 500 ms, `syncWithProductionAPI()` constructs a JSON payload with the ArduinoJson library and posts it via HTTPS (`WiFiClientSecure` with `setInsecure()`, since the production endpoint terminates TLS at Vercel and the firmware does not currently pin certificates). The endpoint is `POST https://walrus-pi.vercel.app/api/esp32/data`, authenticated with a static `X-API-Key` header. The payload schema is:

```json
{
  "device_id": "WALRUS_001",
  "sensors": {
    "basin_temp": 36.5,
    "tds_ppm": 120,
    "float_water_detect": true
  },
  "actuators": {
    "intake_pump_active": false,
    "collect_pump_active": false,
    "peltier_active": true
  },
  "state": "Heating"
}
```

The server's response is parsed into three regions: a top-level `sleep` boolean (manual sleep command), a `commands` object containing the three per-actuator overrides, and a `config` object containing nine runtime-configurable parameters (sleep/wake times, Peltier window, duty-cycle durations, sync interval). The firmware applies all received values to its mutable global state immediately, so app-side configuration changes take effect on the very next fast-loop iteration without requiring a re-flash.

This design — single round-trip POST for both upstream telemetry and downstream commands/config — minimizes radio-on time and avoids the latency of a second request, which is significant on the ESP32 since each new HTTPS connection requires a fresh 250–500 ms TLS handshake.

## 2. Cloud and Server Infrastructure

### 2.1 Technology Stack

The backend is implemented in Python 3.11 using the **FastAPI** web framework and deployed to **Vercel** as a serverless function (handler at `server/api/index.py`). Vercel was selected over self-hosted infrastructure for its zero-configuration HTTPS termination, automatic deployment from Git, and absence of operational overhead — appropriate for a system with bursty, low-volume traffic dominated by a single device. Persistent storage is provided by **Supabase**, a managed PostgreSQL service with built-in row-level security, real-time change-data capture over WebSockets, and an automatically generated REST API (PostgREST). The Python `supabase-py` client is used as a thin wrapper over PostgREST for service-side operations.

The choice of FastAPI is motivated by its native support for Pydantic models, which enforce schema validation at the API boundary — every inbound payload from the ESP32 is automatically parsed, type-checked, and coerced before any business logic executes, eliminating an entire class of malformed-input bugs.

### 2.2 API Design

The HTTP surface area is intentionally minimal, divided into two routers under separate URL prefixes:

**ESP32 Router (`server/api/esp32.py`)** — the only endpoint the firmware contacts.

- `POST /api/esp32/data` — Receives a `ESP32DataPayload` (validated as a Pydantic model: `device_id`, `sensors`, `actuators`, `state`). The handler calls `DataService.store_sensor_data()` to insert one row into the `sensor_readings` table, then immediately calls `DataService.get_device_commands()` to read the current row from `device_commands` for that device, and returns both `sleep`, `commands`, and `config` to the device in a single response. Authentication is enforced by the `verify_esp32_api_key` dependency, which compares the `X-API-Key` request header against a server-side environment variable.
- `GET /api/esp32/test` — A health-check endpoint used during firmware deployment to verify connectivity and credentials.

**Mobile Router (`server/api/mobile.py`)** — exposes read-only convenience endpoints for `/api/mobile/latest`, `/api/mobile/history`, `/api/mobile/status`, and `/api/mobile/stats`. In the current architecture these endpoints are not consumed by the mobile client (which connects directly to Supabase for lower latency and real-time push), but they are retained as a stable RESTful interface for any future third-party integration.

**Sanitization and Validation.** The Pydantic models in `server/models/sensor_reading.py` declare every field as `Optional[T] = None`, allowing the firmware to omit fields it cannot read (e.g., when the DS18B20 returns an out-of-range value) without rejecting the payload. The model's strict type system rejects payloads where a field is present but of the wrong type, and Pydantic's default `extra='ignore'` policy silently discards unknown fields — useful for forward compatibility when the firmware adds a new actuator the server does not yet model.

### 2.3 Data Model

Two tables hold all persistent state. Both reside in the public schema, both have row-level security enabled with permissive policies (`USING (true)`) appropriate for the project's single-tenant deployment, and both are published to the `supabase_realtime` publication so that changes are broadcast to subscribed clients over WebSocket.

**`sensor_readings`** — append-only time-series table; one row per device sync (~500 ms cadence in normal operation).

| Column | Type | Purpose |
|---|---|---|
| `id` | `BIGSERIAL PRIMARY KEY` | Surrogate key, monotonic insert order. |
| `device_id` | `TEXT NOT NULL` | Multi-device support; indexed for fast per-device queries. |
| `basin_temp` | `FLOAT` | DS18B20 reading in °C. |
| `tds_ppm` | `INTEGER` | Temperature-compensated TDS. |
| `clean_level_cm` | `FLOAT` | Reserved for re-introduction of ultrasonic sensor; currently `NULL`. |
| `intake_pump_active` | `BOOLEAN` | Reported actuator state. |
| `collect_pump_active` | `BOOLEAN` | Reported actuator state. |
| `peltier_active` | `BOOLEAN` | Reported actuator state. |
| `float_water_detect` | `BOOLEAN` | Float-switch reading. |
| `state` | `TEXT` | The FSM state string (`Sleeping`, `Heating`, etc.). |
| `created_at` | `TIMESTAMPTZ DEFAULT NOW()` | Insertion timestamp, UTC. |

A composite index on `(device_id, created_at DESC)` accelerates the most common access pattern (newest-first per device). A `latest_reading` view is provided as a convenience wrapper for clients that only want the most recent row.

**`device_commands`** — singleton-per-device row holding both the override commands the firmware should apply and the runtime configuration parameters the firmware should use.

| Column | Type | Default | Purpose |
|---|---|---|---|
| `device_id` | `TEXT PRIMARY KEY` | — | One row per device. |
| `sleep` | `BOOLEAN` | `FALSE` | Manual sleep override. |
| `intake_pump_override` | `TEXT` | `'auto'` | `'auto' \| 'on' \| 'off'`, enforced by CHECK constraint. |
| `collect_pump_override` | `TEXT` | `'auto'` | Same. |
| `peltier_override` | `TEXT` | `'auto'` | Same. |
| `wake_minute`, `sleep_minute` | `INT` | `480`, `1020` | Operating window in PST minutes-of-day. |
| `peltier_start_minute`, `peltier_stop_minute` | `INT` | `630`, `870` | Peltier window in PST minutes-of-day. |
| `peltier_on_minutes`, `peltier_cycle_minutes` | `INT` | `12`, `30` | Duty-cycle parameters. |
| `collect_cycle_minutes`, `collect_duration_seconds` | `INT` | `30`, `5` | Collect-pump duty cycle. |
| `sync_interval_ms` | `INT` | `500` | Firmware fast-loop interval. |
| `updated_at` | `TIMESTAMPTZ` | `NOW()` | Auto-bumped by trigger on any change. |

A `BEFORE UPDATE` trigger (`touch_device_commands_updated_at`) refreshes `updated_at` whenever any column changes, which is consumed by the mobile UI to determine when a user-issued command was last accepted.

## 3. External User Interface (React Native Mobile Application)

### 3.1 Framework

The user-facing client is a cross-platform mobile application written in **TypeScript** with **React Native 0.81** under the **Expo SDK 54** managed workflow. Routing is provided by **Expo Router 6**, which compiles file-system layout to a navigation graph at build time, eliminating the need for a manual route registry. Tab navigation uses `@react-navigation/material-top-tabs` rather than the standard bottom-tabs primitive in order to enable swipe-between-tabs gestures backed by `react-native-pager-view`, producing a touch experience consistent with native iOS and Android conventions.

Application-level state is managed exclusively through **React Hooks** — `useState` for local component state, `useEffect` and `useCallback` for side effects and memoization, `useRef` for mutable handles to subscriptions and animation values, and `useMemo` for derived data and styled-component recreation when the theme changes. Two React Context providers wrap the application root: `ThemeProvider` (controls light/dark/system appearance, persisted via `AsyncStorage`) and `AppSettingsProvider` (holds user-tunable detection and warning thresholds: offline duration, TDS bands, basin-temperature bands).

### 3.2 Component Architecture

The application is organized into four tabs, each implemented as a single screen file under `mobile/app/(tabs)/`:

- **Home (`index.tsx`)** — The primary dashboard. Displays the live device status as a composite pill (e.g., `🟢 Active · Heating`), a power toggle that maps to the `device_commands.sleep` flag, a "Water Quality" section showing the latest TDS reading with semantic coloring against the user's configured warning thresholds, a "Sensors" section with basin temperature and float-switch state, and an "Actuators" section showing the current ON/OFF state of each relay along with any active override and a "Pending" indicator that visualizes the lag between issuing a command and seeing it confirmed in the next telemetry packet. Each card is a `Pressable` that deep-links to the corresponding chart on the Analytics tab via Expo Router query parameters.
- **Controls (`controls.tsx`)** — Three per-actuator cards (Intake Pump, Collection Pump, Peltier), each presenting the three override modes (`AUTO`, `ON`, `OFF`) as large square buttons with state-appropriate color coding. A "Sleep Device" card holds the master power switch. A status banner at the top of the page renders the device's connectivity state and informs the user whether commands will apply immediately, queue until reconnect, or be locked out entirely (when the device is offline).
- **Analytics (`analytics.tsx`)** — A time-range selector (24 h, 7 d, 30 d) drives a paginated query against `sensor_readings` (seek-based pagination over `created_at` to bypass Supabase's `max_rows` cap). Six summary cards aggregate the result set (Operating Time, Pump Cycles, Peltier Runtime, Peak Basin, Avg Purity, Sample Count). Three time-series charts (Basin Temperature, Water Purity, Pump Activations) are rendered with `react-native-chart-kit`, with bucket size automatically adjusted by range (hourly for 24 h, daily for 7 d / 30 d) and labels formatted to never duplicate.
- **Settings (`explore.tsx`)** — A unified preferences page exposing both app-only thresholds (offline detection, TDS bands, basin-temperature bands, theme) and firmware-side runtime configuration (wake/sleep window, Peltier schedule, duty-cycle durations, sync interval). Firmware values are written to `device_commands` and propagate to the ESP32 on its next sync; app-only values are persisted to `AsyncStorage` and applied immediately in-process.

A small set of reusable components — `StatusBadge`, `ActuatorStatusCard`, `Stepper`, `PillGroup` — are shared across screens.

### 3.3 Data Synchronization

Real-time data synchronization is achieved through two independent mechanisms working together:

**Initial fetch.** On screen mount, `walrusAPI.getLatest()` and `walrusAPI.getDeviceCommands()` (in `mobile/services/api.ts`) issue a single REST query against Supabase to retrieve the most recent state. This populates the UI with no perceptible delay on launch.

**Realtime subscription.** Concurrently, the screen subscribes to Supabase Realtime channels for the `sensor_readings` and `device_commands` tables, filtered by `device_id`. When the ESP32 inserts a new sensor row, PostgreSQL's logical replication forwards the change to Supabase's Realtime service, which broadcasts it over WebSocket to all subscribed clients within ~100 ms. The mobile app's callback updates the relevant React state, which triggers a re-render of any component reading that data. The same mechanism applies to `device_commands`: when one user changes an override, all other connected devices see the change live.

**Derived freshness state.** A 5 s `setInterval` in the Home and Controls screens advances a `now` state variable that is fed to `computeDeviceStatus()` (in `mobile/services/deviceStatus.ts`). This function compares the latest reading's `created_at` against the configured offline threshold (default 30 s) and emits one of six status kinds: `active`, `idle`, `sleeping`, `fault`, `offline`, or `unknown`. The status governs not only the visible label and color of the header pill, but also whether the override controls on the Controls page are interactive — a defense against the user issuing commands the device cannot currently receive.

This combination ensures that the dashboard always reflects the most recent data the system has produced, satisfying the project's continuous-monitoring requirement: the user sees critical water-safety parameters update without manual refresh, and changes they make to overrides reach the device within one fast-loop iteration (≈ 500 ms).

## Summary

The WALRUS software architecture cleanly separates the three concerns of an IoT system — physical control, durable storage, and human interface — into independently deployable tiers that communicate exclusively over well-typed, schema-validated JSON contracts. The embedded firmware is a deterministic cooperative loop with a six-state FSM driven by real-time clock and sensor input; the cloud tier is a minimal serverless API delegating storage to a managed PostgreSQL service with built-in change-data capture; and the mobile client consumes that change-data stream directly for sub-second UI freshness. Runtime configuration of the firmware is fully app-controllable, allowing operational tuning without re-flashing the device. The system satisfies the requirement of continuously displaying critical water-safety parameters while maintaining a clean separation of concerns suitable for long-term maintenance and extension.
